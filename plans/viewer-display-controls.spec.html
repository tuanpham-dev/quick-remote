QuickRemote Display Controls

Clients choose how big the remote desktop is (follow the window, or a fixed resolution), how sharp it is (pixel ratio and desktop scale), and how it is shown (fit, fill, 100%, zoom and pan). The host makes the desktop that size: its own virtual display, a virtual monitor on KDE or GNOME, or the real monitor's mode. The round also brings touch gestures, reconnecting, pausing while hidden and fullscreen keyboard lock from the Perch and QuicDesk viewers, and replaces the two rate-control profiles with one adaptive controller so Wi-Fi stops collapsing to 5 fps.

Current state

  • Size: the host resizes only its own sway virtual display, on a Resize request; the web client never sends one. KDE, GNOME and X11 desktops always stream at the monitor's own size.
  • Showing the picture: the web client scales the picture to the page; there is no zoom, pan, fit choice, pixel ratio or desktop scale.
  • Session: after a host restart or network drop the web page stays on "Connection lost"; nothing pauses the stream while the tab is hidden.
  • Touch: Android has a trackpad mode, two-finger scroll, two-finger tap as right click, and a three-finger tap that opens the keyboard. The web client has no touch handling.
  • Rate control: two profiles, picked once per session by private address and a round trip under 30 ms. On jittery Wi-Fi the session lands on Internet, which cuts on every delay rise; the LAN profile cuts 15% per lossy 50 ms window and recovers 5% a second. Either way a loss burst drove fps to 5. Datagram pacing and a keyframe throttle are live on the test host but uncommitted.
  • Reference viewers: Perch's Remote Desktop and QuicDesk follow the tab size, set a pixel ratio with a magnifier button (desktop UI scale follows it), fit the picture to the tab, reconnect with backoff, pause while hidden, offer a phone keyboard with an extra-keys strip, and lock the keyboard in fullscreen.

Scope

In

  • Resolution modes and pixel ratio in the web, native and Android clients
  • Host: sway virtual display, KDE (KWin) and GNOME (mutter) virtual monitors and real-monitor modes, desktop UI scale
  • Fit, Fill window, 100%, view zoom and pan in all three clients
  • Auto-reconnect and pause while hidden in all three clients
  • Touch gestures and phone keyboard on web and Android
  • Fullscreen keyboard lock in the web client
  • One adaptive rate controller, datagram pacing, keyframe throttle

Out

  • Resizing X11 desktops and the Windows host: they keep their size and the client scales to fit
  • Several viewers on one desktop at once (a new viewer still replaces the previous one)
  • Remote cursor shapes as a client-side pointer (the cursor stays drawn into the video)
  • Removing the CPU copy in the KDE/GNOME capture path
  • Image clipboard and file transfer changes

Architecture

Requirements

Resolution and display target
R1Every client offers a Resolution setting: Follow window (default) or Fixed, with presets 1280×720, 1600×900, 1920×1080, 2560×1440, 3840×2160, a custom W×H (even numbers from 640×360 to 7680×4320), and refresh 30, 60 or 120 Hz. R2In Follow window, the requested size is the window's content area (on Android, the screen in the current orientation) multiplied by the pixel ratio, rounded down to even numbers, and sent once the window has been unchanged for 300 ms. R3On KDE and GNOME desktops, every client offers a Display target setting: Virtual monitor (default) or Real monitor. R4With Virtual monitor, the host creates a monitor of exactly the requested size, refresh and desktop scale, streams it, and replaces it when the request changes. Windows on it stay when it is resized. R5A virtual monitor outlives its client by 60 seconds; a reconnect within that time streams the same monitor. After 60 seconds it is removed. R6The client's virtual monitor becomes the primary monitor when the desktop has no physical monitor; otherwise it is added as a secondary monitor. R7With Real monitor, the host switches the monitor to the requested size and refresh when the monitor lists that mode; otherwise the monitor keeps its mode, the client shows it scaled to fit, and the client tells the user that size isn't available. R8On the host's own sway virtual display, both resolution modes resize the display directly (no target setting is shown). R9On X11 and Windows hosts the resolution settings are disabled with a note that this desktop keeps its own size.
Pixel ratio and desktop scale
R10Every client offers a Pixel ratio setting: Auto (the device's ratio, at most 2), 1×, 1.5× or 2×, with the detected device ratio shown next to Auto. R11The host sets the desktop's UI scale to the pixel ratio (rounded to the nearest scale the desktop supports) on the sway virtual display, KDE monitors and GNOME monitors, so apps keep their apparent size.
Showing the picture
R12Every client offers three view modes: Fit (default: shrink to fit, never enlarge), Fill window (fit, enlarging allowed) and 100% (one remote pixel per device pixel, panned when larger than the window). Aspect ratio is always kept. R13View zoom from 25% to 400%: Ctrl+wheel and +/− controls on desktop clients, pinch on touch screens; when the zoomed picture is larger than the window it pans (drag with the scroll gesture, scrollbars or edge-follow on desktop). R14Pointer and touch positions reach the remote desktop at the point under the finger or cursor at every zoom level, view mode and pan position. R15All display and view settings persist per browser (web) or per device (native, Android) and apply on the next connection.
Session
R16When the connection drops, the client keeps the last picture, shows "Reconnecting…", and retries after 1, 2, 4, 8 and then every 10 seconds, without asking for the PIN when it is paired. R17While the web tab is hidden, the native window is minimized, or the Android app is in the background, the host sends no video; on return the picture resumes with a fresh keyframe within one second.
Touch and keyboard
R18Touch gestures on web and Android: tap = left click, long press (500 ms without moving) = right click, two-finger tap = right click, two-finger drag = scroll, three-finger tap = middle click, pinch = view zoom, four-finger tap = show or hide the keyboard. R19On touch devices a toolbar holds Keyboard, Zoom and Display buttons. The keyboard comes with an extra-keys strip: Esc, Tab, arrows, Home, End, PgUp, PgDn, and sticky Ctrl, Alt and Super that apply to the next key. R20In web fullscreen on Chromium browsers, browser shortcuts (Ctrl+T, Ctrl+W excepted, Alt+Tab where the OS allows) go to the remote desktop, and holding Escape for one second exits fullscreen.
Rate control
R21One adaptive rate controller serves every connection, local or internet: it raises the bitrate while delivery is clean, backs off on loss that error correction cannot repair or on a steadily rising delay, and tolerates jitter without backing off. R22Each frame's datagrams are paced instead of sent in one burst, and forced keyframes are at most one per 250 ms (or two round trips, whichever is longer). R23The host still accepts --profile, ignores it, and prints a warning that it has no effect.

Flows and edge cases

  • Dragging the window edge: the picture scales live (view only); 300 ms after the edge stops, the host resizes. On KDE/GNOME the picture briefly shows the old size scaled until the new monitor's first frame (about 0.3–0.5 s).
  • Switching Virtual to Real monitor mid-session: the virtual monitor's 60-second timer starts and the stream switches to the real monitor.
  • Fixed size larger than the window: Fit shrinks it; 100% shows it at native size with panning.
  • Real monitor without the mode: the setting keeps the requested size but shows "Not available on this monitor, showing 1920×1080 scaled".
  • Host restarted: reconnect finds a new host process; virtual monitors from the old process are gone, so a new one is created.
  • Sticky modifiers: tapping Ctrl lights it; the next key is sent with Ctrl held, then Ctrl releases. Double-tap locks it until tapped again.
  • Long press: moving more than 10 px before 500 ms cancels the right click and starts a drag instead.

Risks

  • KWin and mutter virtual monitor details (scale, refresh, making it primary, removal) are untested here. Handling: verify each with the headless test desktops early; if one isn't possible, note it in the client and keep the rest.
  • Keyboard lock and phone keyboards vary by browser and device. Accept: test on headless Chrome and the Android emulator; real devices may differ.
  • One controller for LAN and internet needs retuning of the existing WAN tests' expectations. Accept: A18 keeps them as the bar.
