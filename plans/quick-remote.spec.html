QuickRemote: remote desktop and LAN game streaming

Project: /works/quick-remotePlan: plans/quick-remote.md2026-10-02Status: awaiting review

§1Summary

QuickRemote is a new, clean-room remote desktop app with its own protocol. On a LAN it streams at gaming quality (up to 1080p120 or 4K60, about 20 ms end to end) with audio, gamepads and raw mouse input. Over the internet it reaches hosts behind home routers through a self-hosted rendezvous and relay server. Hosts run Linux (virtual or real desktop) and Windows. Clients are a native desktop app, a web page and an Android app.

§2Current state

  • /works/quick-remote is empty. Nothing is reused from /works/quicdesk. That project serves as a reference only; its lessons (one frame per QUIC stream, nothing encoded that can't be sent, frame rate drops before quality) inform the design.
  • Build and test machine: Debian 13, Intel i5-9500 (6 cores), 15 GB RAM, Intel UHD 630 with VA-API. The GPU encodes H.264 and HEVC in hardware but not AV1. GStreamer VA-API, Rust, Node 24 and gcc are installed.
  • The machine is headless. It has no physical desktop session, no second LAN machine, no Windows PC, no discrete GPU and no Android device. You'll provide hardware later, and every phase that needs it has a hardware gate.

§4Scope

In

  • Wire protocol, its specification document and a conformance test suite
  • Linux host: virtual GPU display, X11 desktop, Wayland desktop through the screencast portal
  • Windows host (Windows 10 21H2+ and Windows 11)
  • Native client for Linux and Windows
  • Web client for desktop Chrome, Edge and Firefox
  • Android client for Android 10+ phones, tablets and TVs
  • Rendezvous and relay server
  • Video, audio, microphone, keyboard, mouse (absolute and relative), gamepad, pen, clipboard, files, multi-monitor
  • Optional host system service: login and lock screen, UAC, autostart
  • Stats overlay and a latency measurement tool

Out (non-goals)

  • Stereo 3D and VR headset streaming
  • User accounts and cloud host lists
  • macOS host and macOS client; iOS client
  • HDR (10-bit PQ) streaming
  • Several clients controlling one host at the same time, and view-only spectators
  • Compatibility with RDP, VNC or Moonlight clients
  • Session recording
  • Bypassing game anti-cheat that blocks virtual input devices
  • App store publishing (Play Store, Microsoft Store)

§5Architecture

§6Requirements

Connection and security

R1A running host advertises itself on the LAN, and a client on the same subnet lists it within 3 s without the user typing an address.
R2The first connection between a client and a host requires a 6-digit PIN shown on the host. After pairing, each side stores the other's public key, and later connections need no PIN. A client that isn't paired and doesn't present the PIN is refused.
R3All session traffic is encrypted end to end with TLS 1.3 and authenticated by the paired keys, including when it passes through the relay. The relay cannot read or alter it.
R4Over the internet, a client reaches a paired host by its host ID through the rendezvous server, with no port forwarding. The path is direct when hole punching succeeds and relayed otherwise, and the client shows which one is in use.
R5The rendezvous and relay server ships as one binary and one Docker image. Hosts and clients work fully on a LAN without it.
R6A dropped session reconnects automatically within 5 s of the network coming back, without a new PIN, and on reconnect all held keys and buttons are released on the host.

Video and 3D

R7The host picks the most efficient codec both sides decode, ranked AV1, then HEVC, then H.264. It uses a hardware encoder when one opens and a software encoder otherwise. The chosen codec and encoder are shown in the stats overlay.
R8LAN profile: at 1080p60, the time from host capture to client present is ≤ 20 ms at p95 and ≤ 12 ms at the median. On hardware whose encoder supports it, 1080p120 and 4K60 run at full frame rate within the same budget.
R9Internet profile: on a 10 Mbps link with 50 ms RTT and 1% random loss, the stream never freezes for more than 500 ms and settles to a stable rate within 5 s. When the link shrinks, frame rate drops before per-frame quality, and the stream recovers when the link grows.
R10Forward error correction repairs random packet loss up to 5% (LAN) or 10% (internet) without retransmission or a new keyframe. When a frame can't be repaired, the host restores a clean picture within one RTT plus one frame.
R11Sharp-text mode (toggle in the client) sends 4:4:4 chroma when the encoder supports it. Otherwise, 300 ms after the screen goes still, it sends one high-quality refresh frame.
R12On GPU backends, frames travel from capture to the encoder without a copy through system memory. A GPU-rendered 3D app running at 60 fps on the host streams at 60 fps.
R13Virtual display: the host can start a headless GPU-accelerated display at the resolution and refresh rate the client asks for (up to 3840×2160 at 120 Hz) and run a desktop session or a single app or game in it.
R14Real desktop: the host captures an existing Linux X11 session, a Linux Wayland session through the screencast portal (asking permission once, then remembering it), and the Windows desktop.
R15Multi-monitor: the client lists the host's monitors and streams the chosen one, can switch monitors during a session, and can open a second window streaming another monitor.
R16When the client window is resized, the virtual display follows it. For a real desktop, the client scales the picture to fit with the aspect ratio kept.

Audio

R17Host audio (stereo, 48 kHz, Opus) plays on the client with ≤ 40 ms of added latency on a LAN, and audio and video stay within ±40 ms of each other.
R18The client's microphone, when the user turns it on, appears on the host as a microphone input that host apps can record from. It is off by default.

Input

R19Keys are sent by physical position, so games and shortcuts work whatever the keyboard layouts on either side. A separate text mode types committed characters for phone keyboards and IMEs.
R20Mouse has two modes. Absolute is for desktop work. Relative is for games: the pointer is locked, raw deltas are sent, and the client adds no acceleration. A hotkey switches modes, and the host's request to capture the pointer switches automatically.
R21Up to 4 client gamepads appear on the host as virtual Xbox-style controllers with all buttons, sticks and triggers. Rumble returns to the client. Plugging and unplugging is reflected during a session.
R22Pen input from a client tablet arrives on the host as a pen with pressure (at the client device's full resolution), tilt and an eraser.
R23Input reaches the host within 2 ms of the client receiving it, plus one-way network time. Losing a packet never leaves a key or button stuck.

Desktop features

R24Clipboard text and images (PNG, up to 16 MB) sync both ways. It is on by default and can be switched off per host.
R25Files move both ways: by drag and drop in the native client and through a file picker in the web and Android clients. Transfers show progress, can be cancelled, are checked against a hash on arrival, and never block video or input.

Clients

R26The native client runs on Linux and Windows. It shows the host list (discovered, paired, by ID), runs sessions in a window or fullscreen, and decodes in hardware with a software fallback.
R27The web client is served by the host. It runs in desktop Chrome, Edge and Firefox over WebTransport with WebCodecs, and supports video, audio, keyboard, mouse with pointer lock, gamepads, clipboard and file upload and download.
R28The Android client runs on Android 10+. It decodes in hardware, supports touch as mouse (trackpad and direct modes), the on-screen keyboard, Bluetooth and USB controllers, a hardware mouse and keyboard, and pen input, and works with a TV remote on Android TV.
R29Every client has a stats overlay toggled by a hotkey. It shows fps, bitrate, codec, path (LAN, direct or relay), packet loss, FEC repairs and latency split into capture, encode, network, decode and present.

Hosts and operations

R30The Windows host captures through Windows Graphics Capture (with DXGI duplication as a fallback), encodes on NVENC, AMF or Quick Sync, injects input with virtual gamepad and pen devices, and captures audio by WASAPI loopback.
R31The host runs as an app in the logged-in user's session. The optional system service also reaches the login and lock screens (and UAC prompts on Windows) and starts at boot.
R32The protocol has a written specification with a version number. A conformance suite checks the Rust core and the web client against it, and peers with different major versions refuse each other with a clear message.

§7Behavior and UX

Flows

  1. First pairing (LAN). Start the host, which shows its name and a 6-digit PIN. Open the client and the host appears under "On this network". Choose it, enter the PIN, and the session starts. The host is now listed under "Paired".
  2. Internet. On the host, turn on internet access and enter the rendezvous server address; the host shows its host ID. On a paired client, add the host by ID once, or have it filled in automatically when pairing happened on the LAN. Connecting shows "Direct" or "Relayed".
  3. Game session. Click into the stream. The first click in a game that hides its cursor locks the pointer, and the hotkey releases it. Gamepads connected to the client show up on the host immediately.
  4. Leaving. The hotkey or the window close button ends the session. The host releases every held input and, for a virtual display, keeps running or stops according to the host setting.

States and errors

  • Connecting → Direct / Relayed / LAN → Reconnecting → Ended. The current state is always shown in the title bar and the overlay.
  • Wrong PIN: "That PIN doesn't match. Check the code on the host and try again." After 5 wrong attempts a minute, the host ignores that client for 60 s.
  • Host unreachable by ID: "The host isn't online on the rendezvous server. Check that the host is running and has internet access turned on."
  • No common codec: the error names the codecs each side has.
  • Wayland permission refused: the host says capture needs the screen-sharing permission and offers to ask again.
  • Version mismatch: "This host runs protocol vX; update the client (or the host)."

§8Acceptance criteria

Simulated LAN means two Linux network namespaces joined by a veth pair on this machine, shaped with netem. Criteria tagged hardware gate are checked when the named hardware is connected. Until then they are reported as "environment-blocked", never as passed.

§9Risks

RiskHandling
Only the UHD 630 is available. 1080p120, 4K60, AV1, Windows, Android hardware decode and real-LAN glass-to-glass can't be measured yet.Accept: each one is a hardware gate (A9, A15, A26, A28, A30, A31), reported as environment-blocked until you connect the hardware.
Even the UHD 630 at 1080p60 may miss p95 ≤ 20 ms if VA-API encode plus loopback decode costs more than budgeted.Investigate: measure encode cost in the first task of Phase 1. If it misses, the spec target stays, and A8 reports the measured number and its breakdown.
The Windows virtual gamepad driver (ViGEmBus) is archived upstream.Investigate at the start of Phase 4: ViGEmBus as shipped, versus a signed Virtual HID Framework driver. The choice comes back to you before building.
Wayland portals differ between GNOME, KDE and wlroots, and some ask for permission every time.Mitigate: restore tokens where supported; otherwise a one-time prompt per session, documented.
Symmetric NAT on both ends defeats hole punching.Accept: relay fallback (R4). Relay bandwidth is the operator's cost.
Anti-cheat in some games rejects virtual input devices.Accept: out of scope.
Browser decode and present add 1–2 frames of latency over native.Accept: R8 applies to the native client. The web client reports its own numbers.
Overall size: five phases, three host types and three clients.Mitigate: every phase ends usable, and the plan is the resumable tracker across sessions.
